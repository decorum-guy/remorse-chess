# Realtime R3: очередь запуска, ресурсы и долговечная запись

## Статус и основание

Документ описывает изменения, непосредственно прочитанные в исходниках, и реально завершённые проверки. Это следующая редакция после [предыдущего сетевого отчёта](VALIDATION_FORPOST_REALTIME_2026_11_28.md), а не переоценка его результатов. Два ранее остановившихся четырёхкомнатных прогона остаются **FAIL**. Новый часовой прогон, принятая производственная ёмкость, собственный браузерный проход и публичный выпуск этим документом не подтверждаются.

Требования: [REALTIME_PLATFORM](../game-design/REALTIME_PLATFORM.md), §3 и §11; [EXECUTION_PROTOCOL](../game-design/EXECUTION_PROTOCOL.md). Изменения совместимы с существующими API платформы, Chess и District. Для Forpost добавлены необязательный идентификатор хозяина в замороженную команду запуска и необязательное поле ожидания в представление комнаты. Старые записи остаются читаемыми.

## Запуск и резерв

`rt_start_queue` хранит порядковый номер, неизменяемый `startId`, отпечаток команды, доверенный идентификатор хозяина и резерв. Очередь ограничена 128 строками; один хозяин может иметь только один ожидающий старт. Уже играющий матч не мешает хозяину поставить один следующий старт в очередь.

`PlatformService` берёт `hostPlayerId` из авторизованного actor в момент запуска. Клиентское поле хозяина отвергает существующая строгая HTTP-схема. Runtime проверяет, что переданный хозяин является человеком в замороженном составе. Старые команды без этого поля используют общий ключ `account:legacy`; это ограничивает параллельное ожидание старых клиентов, но не приписывает полномочия первому месту состава.

FIFO выбирает только голову очереди. При достаточных ресурсах SQLite записывает резерв с TTL 15 секунд. Повтор того же старта у того же владельца использует существующие token и deadline, не продлевая TTL. Другой владелец не получает действующий резерв. После истечения срока новый token сохраняет прежнее место в очереди. Транзакция создания проверяет token, owner и срок, записывает матч и начальный checkpoint, затем удаляет строку очереди. Повтор уже созданного `startId` возвращает тот же матч; изменённый отпечаток получает `START_CONFLICT`.

Раз в секунду runtime повторно рассматривает очередь. Запуск продолжается после освобождения ресурсов без создания новой команды платформой. Drain блокирует новые allocation, ждёт уже начатую операцию и сохраняет очередь. После рестарта очередь читается из SQLite. Оставшийся резерв другого процесса сохраняет исключительность до TTL.

Гостевая тренировка не запускается позднее без своего HTTP-запроса. Если её create получил busy, строка ожидания отменяется. Остаток гостевого старта после аварии удаляется после окончания резерва. Это предотвращает невидимые комнаты, которые пользователь не смог бы открыть из потерянного ответа.

Для account-room HTTP 503 несёт безопасный `waiting`, который адаптер проверяет и передаёт платформе:

```ts
type StartWaiting = {
  reason: 'capacity' | 'updating' | 'another_start' | 'service';
  retryAt: number;
  queuePosition?: number;
  reservationExpiresAt?: number;
};
```

Платформа сохраняет ожидание вместе со следующей попыткой сверки, повторяя исходный `startId`. Поле `room.startWaiting` позволяет UI показать реальную причину и позицию. `retryAt` означает момент повторной проверки, а не обещание свободной комнаты.

## Бюджет ресурсов

Профиль загружается из `REALTIME_CAPACITY_PROFILE_PATH`. Ни одного принятого производственного профиля в репозитории нет. Без подходящего профиля эффективный лимит — одна комната; настройка `REALTIME_MAX_ROOMS=4` сама по себе его не повышает.

| Поле профиля | Значение и ограничение |
| --- | --- |
| `schema`, `gameId` | `iva-realtime-capacity-1`, `forpost` |
| `artifactId` | Точный hash runtime; профиль другой версии не переносит её ёмкость на новый код |
| `source` | `measured` либо `test-fixture`; второй вариант запрещён при `NODE_ENV=production` |
| `evidence` | Ссылка или обозначение фактического отчёта; строка не заменяет сам отчёт |
| `maxRooms` | От 1 до 16, дополнительно ограничено `REALTIME_MAX_ROOMS` |
| `maxBodies`, `maxBots`, `maxConnections` | Общий измеренный допустимый состав |
| `roomMemoryBytes` | Предельная память на комнату из профильного измерения |
| `stepP99Ms` | p99 wall-времени шага для профиля; не равен CPU-времени |
| `cpuMsPerTick?` | CPU всего процесса за интервал, делённый на число подтверждённых room ticks за тот же интервал |

При отсутствии `cpuMsPerTick` расчёт ожидаемой вычислительной нагрузки консервативно использует `stepP99Ms × 30`. Одновременная нагрузка также учитывает наблюдаемый CPU процесса. Для профиля нужен измеренный целевой стенд, сцены и принятая нагрузочная проверка. Валидность JSON и слово `measured` не доказывают соблюдение этих условий.

Одна максимальная комната резервирует 56 тел: у каждого из шести участников боец, строитель, два дрона и пять построек, плюс два транспорта. В бюджете ботов учитываются все места, поскольку человек может временно перейти под управление бота. На человека резервируются два соединения; дополнительные уже существующие view-only соединения тоже входят в проверку.

`ResourceProbe` читает числовые cgroup v1/v2 quota, limits и current usage, включая текущую группу и доступные предки. CPU ограничен самой строгой quota, доступной affinity и двумя simulation workers. Нельзя подменять quota числом процессоров машины. При неизвестной quota используется консервативное значение одного CPU. Если лимит памяти неизвестен, используется максимум 1 GiB с дополнительным ограничением реальной доступной памятью процесса/машины. Это ограничение admission, а не утверждение о выделенном VPS.

Перед добавлением комнаты сохраняются минимум 30% вычислительного бюджета и 25% RAM. Для памяти учитывается каждый ограниченный предок: почти заполненный родитель с большим лимитом не маскируется свободным дочерним лимитом. Неизвестный current при известном лимите запрещает новый admission. Расчёт также использует реальный RSS, свободную память и зарезервированную память существующих комнат. Отставание активного матча свыше 100 мс блокирует новые старты, не меняя правил уже играющих комнат.

`network-smoke.mjs` содержит явно помеченный `source: test-fixture` с двумя слотами для функциональной проверки одновременного сохранения старой и новой версии. Его синтетические размеры не названы измеренной ёмкостью; ресурсы процесса при этом читаются настоящим probe. В unit-тестах используются отдельно обозначенные фиктивные числовые samples для проверки арифметики и крайних случаев.

## Writer и публикация

Выявленная структурная стоимость старой реализации — отдельная SQLite `synchronous=FULL` транзакция на каждый тик каждой комнаты. Теперь writer имеет ограниченное FIFO-группирование:

1. Не более 2 мс на накопление входящих запросов перед flush.
2. Не более 64 запросов за flush; остаток передаёт управление event loop.
3. Не более 32 соседних `commit` в одной внешней транзакции; чтение или другая операция образуют границу.
4. Savepoint каждой комнаты изолирует известный конфликт lease/checksum/constraint. Неожиданная ошибка SQLite откатывает всю группу.
5. Ни одна квитанция не отправляется до успешного завершения внешней транзакции.

Подготовленные SQL statements кэшируются. Порядок записей, fencing, атомарные receipt/outbox и прежняя граница публикации сохранены. Working world не попадает в snapshot/результат до подтверждения записи. Это материальное изменение механизма writer, но его выигрыш на целевом сервере ещё не измерен этим отчётом.

## Наблюдаемость и отсутствие людей

| Метрика | Что именно измеряет |
| --- | --- |
| `stepP99Ms` | RPC от dispatch до возвращения результата worker, включая очередь/передачу |
| `stepWorkP99Ms` | Wall-время работы внутри simulation worker: шаг, сериализация и безопасные views |
| `stepWorkCpuP99Ms` | CPU текущего worker-thread за ту же работу, без сетевого цикла и writer |
| `processCpuMs` | Накопленный CPU всего Node-процесса со всеми threads; для профиля нужна разность за тот же интервал, что ticks |
| `commitP99Ms` | Время ожидания writer acknowledgement |
| `journalPendingAgeMs` | Возраст самого старого ещё не опубликованного tick/control write |
| `journalAgeP99Ms` | Завершённые интервалы от dispatch до долговечности |
| `snapshotAgeMs`, `snapshotAgeP99Ms` | Возраст опубликованного состояния активных комнат; paused/countdown не считаются сетевым отставанием |
| `resyncReasons` | Requested, stale epoch и backpressure |
| `maxCommitBatchSize` | Наибольший реально подтверждённый batch |

Тайминги доступны и в `byGame.forpost`. Очереди конкретных соединений и строки ожидания доступны только в авторизованной maintenance-диагностике. Публичный health содержит инфраструктурные агрегаты, не world, позиции, экономику или боевые статистики.

Первоначальный handoff не тикает без клиента: созданный матч остаётся `ready`, tick 0. Пять секунд без активности human-controller включают временного бота; десять секунд без человеческого присутствия долговечно приостанавливают комнату. После записи клиент получает `phaseChanged` с причиной `NO_HUMANS`. Native WebSocket pong не заменяет прикладную активность: зависшая игровая вкладка не должна бесконечно считаться присутствующей. Эти сроки не ослаблены ради маскировки browser/performance failures.
